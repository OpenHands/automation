Design proposal · automation-scoped outcomes

Store agent-submitted JSON outcomes in the automation service.

This page proposes a scoped outcome API that mirrors the automation KV access model. Scripts and agents submit JSON to the automation service; the service stores raw submissions, optionally parses configured keys, rejects bad parses, and exposes typed values for automation-level analytics.

Design goal

Keep outcomes automation-scoped for now. The automation service is the durable owner because dashboards need to query by automation_id, and cloud sandboxes are not authoritative storage.

The agent server or script should be a submitter only. The canonical records and analytics projection live in the automation service database.

What this solves

  • Agents can report outcomes without relying on a final tool call.
  • Custom scripts can report deterministic results at the point they know them.
  • Automation authors can configure parser keys once per automation.
  • OHE and Canvas can aggregate by automation ID.

What this avoids

  • No generic conversation-wide outcome system yet.
  • No per-agent finish-tool JSON schema requirement.
  • No analytics fan-out across ephemeral sandboxes.
  • No arbitrary DB JSON-path queries for core dashboards.

API shape

The endpoint should follow the KV model: a per-run token grants access to one automation. User auth can still inspect or submit with an explicit automation_id for administrative/debug paths.

POST /api/automation/v1/outcomes
Authorization: Bearer $AUTOMATION_OUTCOME_TOKEN
Content-Type: application/json

{
  "payload": {
    "repository": "OpenHands/automation",
    "pull_request": 770,
    "reviewed": true,
    "comments_posted": 4
  }
}

For user-authenticated calls:

POST /api/automation/v1/outcomes?automation_id={automation_id}
X-Session-API-Key: ...

{
  "run_id": "optional-run-id",
  "payload": {...}
}

The dispatcher can inject these variables into automation runs, using the same signed claims model as KV:

AUTOMATION_OUTCOME_URL=https://.../api/automation/v1/outcomes
AUTOMATION_OUTCOME_TOKEN=<signed automation/run-scoped JWT>

Overall architecture

Submitted outcomes go to the automation service. It validates access, loads the automation's parser config, stores the raw payload, then stores key/value rows used by analytics.

Parsing contract

No parsers configured

The service stores each top-level incoming JSON field as a key/value row. Nested objects and arrays are stored in value_json only.

{
  "reviewed": true,
  "comments_posted": 4,
  "repository": "OpenHands/automation"
}

Parsers configured

The service evaluates each parser. If expression evaluation fails, returns null/missing, or does not match the declared type, the endpoint returns 422 and stores nothing.

outcome_parsers: [
  {
    "key": "github.repository",
    "expression": "subject.repository",
    "value_type": "string"
  },
  {
    "key": "review.comments_posted",
    "expression": "outcome.comments_posted",
    "value_type": "number"
  }
]
This is stricter than finish-response extraction. A bad outcome submission should fail immediately so the script or agent can correct it.

Aggregation by automation ID

Analytics reads from automation_outcome_values, not from arbitrary JSON paths. This keeps cloud and local storage portable and indexable.

GET /api/automation/v1/{automation_id}/outcomes/aggregate
  ?key=review.comments_posted
  &operation=sum
  &since=2026-11-01T00:00:00Z
  &group_by=day
QuestionKeyOperation
How many PR review outcomes were submitted?review.reviewedcount_true
How many review comments were posted?review.comments_postedsum

Rollout plan

  1. Add automation config field outcome_parsers.
  2. Add automation-scoped outcome token/env injection beside KV token injection.
  3. Add POST /v1/outcomes with token and user-auth paths.
  4. Persist raw submissions and typed values in the automation DB.
  5. Add list and aggregate endpoints scoped by automation_id.
  6. Update common OSS automation helpers to submit deterministic outcomes.

Finish-tool extraction can remain as an optional compatibility path, but this outcome API should become the primary contract for durable automation impact analytics.
