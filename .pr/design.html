PR #446 · reviewer guide

Continue Slack threads by durable ownership

Slack threads are flat: parent_user_id identifies the thread-root author, so payload inspection alone cannot prove that a human reply follows a bot response. This change accepts human thread replies as candidates and lets the existing AutomationRun.subject_key decide whether the service owns the conversation.

1The database, not process memory, is the trust boundary

★ A human-rooted reply may continue an already-owned subject, but it cannot create a new run. Bot-rooted replies retain the issue’s original new-run behavior.

The Slack provider marks ambiguous human-rooted messages with existing_subject_only=True. Ingestion still resolves the automation’s configured subject expression and calls the existing conversation router; if no active run owns that exact subject, it stops before create_automation_run(). Sources: streams/slack.py:150 · ingest.py:169

ⓘ The ownership record is already durable and shared by replicas. No process-local “threads the bot has seen” cache or new migration is introduced.

2The normal human-rooted conversation now survives

Before-state source: streams/slack.py:140. After-state sources: streams/slack.py:140 · ingest.py:176.

Human-rooted threaded messageexisting_subject_only=TrueContinue only when subject_key is already owned

This is additive to the internal AcceptedEvent dataclass and defaults to false, so HTTP webhooks and every existing stream event retain their current fallback behavior. Sources: ingest.py:40 · test_ingest.py:587.

⚠ An automation must listen for both app_mention and message, use destination: continue_conversation, and derive the same Slack thread subject for both. Existing app-mention-only automations remain unchanged.
