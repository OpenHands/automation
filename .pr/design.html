Design review · Issue #342 · Phase 1

A run now remembers the source it actually launches

Source provenance moves from the mutable automation definition onto the run itself. The dispatcher freezes the snapshot when it claims the run, and execution consumes that snapshot—even if the automation changes afterward.

3Claim time is the consistency boundary

Sources for this section
snapshot_run_source():53–65 · dispatch_pending_runs():568–592

Stamping only at creation would be inaccurate under existing semantics: an automation can change while its run waits in the queue, and the dispatcher historically uses the latest definition. The snapshot is therefore initialized at creation, then refreshed immediately before the PENDING → RUNNING transition and committed with it.

ⓘ Why not freeze at creation? That would silently change existing queue semantics by forcing an older definition to execute after an edit. Claim-time freezing adds provenance without making that product change.

Sources: creation snapshot · run.py:216–226 · claim snapshot · dispatcher.py:578–592

7This enables rollback decisions; it does not make them

Issue #342 deliberately separates run stamping from Git ref support and restore behavior. This PR lands only the independently useful observation primitive.

Stamp runs with tarball and trustworthy commitIncluded

⚠ Not full reproducibility: this snapshot does not freeze entrypoint, model, secrets, runtime image, or dependency resolution. A tarball path is source provenance; this PR does not guarantee the referenced artifact is retained forever.

The issue's remaining questions—restore granularity, unpin behavior, manual versus automatic rollback, “last good” semantics, watcher authority, and URL normalization—remain product decisions. Nothing in this schema forces an answer.
