Automation runs now leave queryable impact facts behind.

This PR adds a small analytics substrate: automation authors define facts to extract from the finish response, successful runs persist those facts, and Canvas/OHE can query raw values or aggregates without hard-coding one dashboard shape.

What changed

The design is additive: Automation stores optional impact metric definitions, each completed run stores one fact row per metric, and read APIs return raw fact rows or grouped aggregates.

★ Review complete_run() and AutomationRunImpactValue first. They define when facts are written and how analytics reads them.

Before

Run completion saved status, timestamps, status detail, conversation id, and a copy of the finish tool response inside run metadata. Analytics consumers had to parse nested metadata.

After

Metric definitions are validated on create/update, then successful run completion extracts typed values into indexed fact rows. Consumers can list values or request sum/avg/min/max/count aggregates.

API before → after

Before

POST /api/automation/v1
{
  "trigger": {...},
  "observability_associations": {...}
}

GET /api/automation/v1/{id}/runs
// No dedicated impact metric read model.

After

POST /api/automation/v1
{
  "trigger": {...},
  "impact_metrics": [{
    "key": "code_reviews_created",
    "label": "Code reviews created",
    "expression": "metrics.code_reviews_created || `0`",
    "value_type": "number",
    "default_aggregation": "sum"
  }]
}

GET /api/automation/v1/{id}/impact/values
GET /api/automation/v1/{id}/impact/aggregate

Compatibility verdict: additive. Existing automations can omit impact_metrics, and existing run metadata remains unchanged. The new field is threaded through raw creation, prompt/plugin presets, plugin-spec creation, and git-sync import/export.

Run completion flow

The main behavior change is the new fact table written from a successful completion callback.

Risk notes

  • Metric extraction is best effort: a bad metric stores an extraction error row instead of failing run completion.
  • Only successful completions produce facts: the write occurs after the status update/reconciliation path accepts the callback.
  • Aggregation is intentionally simple: this first slice supports numeric operations plus count and can evolve without changing stored facts.
Compact review checklist
  • Check that all create paths preserve impact_metrics.
  • Check that org scoping is applied to read endpoints and fact rows.
  • Check that migration indexes match expected analytics queries.
  • Check that duplicate callbacks do not duplicate fact rows.
